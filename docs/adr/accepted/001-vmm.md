# ADR-001: the VM layer

status: proposed

## Context

A7 forbids writing a VMM and caps the backend interface at six methods; A6 wants one static Go binary on the host; P3 allows no
host dependency beyond KVM or Virtualization.framework; P6 names macOS arm64, Linux amd64 and Linux arm64; P1 wants a warm start
p50 under 1.0 s on a developer machine, 2.5 s on a hosted runner. B2 makes the VMM and the guest kernel `trusted` pins: the SPEC
expects them fetched by digest, not linked in. U-100 to U-102 measured every candidate alike (static Go guest as PID 1 of an
initramfs, raw virtio-blk share, one vsock port map, no network device, 2 vCPU, 1024 MiB, 20 timed boots); `total_ms` is the first
vsock byte minus the instant before the first host process starts. Linux numbers are one hosted gate run (U-101), Mac numbers an
M2 Max over two runs; a Linux number compares with a Mac number only within P1's own two classes.

## Decision

- Linux amd64 and arm64: Firecracker, exec'd by the per-session supervisor. macOS arm64: Virtualization.framework through
  Code-Hex/vz, inside the supervisor process. One recommendation, two packages under `internal/vmm`, one interface. libkrun is
  fastest everywhere but fails A6 and P3 on both hosts as shipped, its 1.x API is being replaced, and it still needs a child
  process of ours. Cloud Hypervisor is the Linux fallback should virtio-fs there become a must: the same six methods, one pin
  row, a host floor of 6.8 and a virtiofsd we would build. vfkit is vz one process away, for a 66 MB pin. Apple container fails
  A9 and P3 by construction. Every row meets P1 with margin, so speed below 0.3 s buys nothing against A6 and P3.
- Process and A9. Linux: the supervisor execs `firecracker` with `Pdeathsig=SIGKILL` from a goroutine locked to its thread (the
  signal follows the forking thread), rlimits on the child (I10), default seccomp, no jailer (it needs root). The device model is
  in the child, so a VMM fault cannot take the supervisor and its log with it. macOS: the VM lives in the supervisor and dies
  with it (measured; Apple's helper holds the devices). The `workcell` binary is signed with `com.apple.security.virtualization`,
  ad hoc in development and in the gate, Developer ID at H-703; `com.apple.vm.networking` is not needed.
- Delivery (A6, B2, B8, P3). Firecracker, the kernel and the guest image are `trusted` pin rows per architecture, fetched on the
  host by pinned URL and SHA-256 under the channel manifest (ADR-004) and kept beside the image: the project redistributes nothing,
  the GPL kernel included, and the user installs only the hypervisor. Firecracker's release checksums are checked at bump time
  (B5). vz is a Go module: Dependabot, 7-day cool-off, tags only, so v3 until a v4 is tagged.
- One guest image per architecture serves both OSes: a read-only virtio-blk image, which every backend booted. One kernel per
  architecture must boot on Firecracker and, for arm64, on VZ: B fails on VZ; A boots everywhere but has no release and no
  timestamps, so it cannot be a B3 pin; C (tagged, both arches, virtio-fs) boots on VZ and is U-201's first candidate on
  Firecracker. Linux arm64 is the same code with Firecracker's aarch64 asset and the arm64 kernel and image that macOS uses;
  H-704 checks it (nested virtualization needs an M3 and macOS 15; U-102's Mac is an M2 Max).
- Shares. The workspace export is a virtio-blk device on every backend; nothing relies on virtio-fs, which Firecracker lacks. No
  backend gets a network device: vsock is the only channel (measured: `lo` only, host loopback unreachable, I4) and ADR-003 builds
  the network path on it. Exit code and shutdown go over the channel: the init (U-203) powers off on host disconnect, and the
  supervisor's deadline and then `Kill` enforce it (A1), so no backend method asks the guest for anything.
- `internal/vmm.Machine`, six methods. A backend's `New(cfg)` takes `Config` (kernel, image, workspace disk, CPUs, memory, a
  host-built command line with no secret in it (I5), console writer, CID) and boots nothing. `Check(ctx) error`: `/dev/kvm`
  writable and the pinned binary present, or `kern.hv_support` and the entitlement; `doctor` calls it alone. `Listen(port)
  (net.Listener, error)`: guest-initiated vsock connections to one port, before Start (unix socket `<vsock>_<port>` for
  Firecracker, `VirtioSocketDevice.Listen` for vz). `Start(ctx) error`: boot. `Wait(ctx) error`: block until the guest has
  stopped, and say why. `Kill() error`: destroy now, idempotent. `Close() error`: remove what the backend made (sockets, handles),
  nothing of the supervisor's (I7). No seventh: stop, exit code and network go over the channel, caps into Config, fetching to pins.

## Consequences

- Budget: direct modules 2 of 15 after cutover (vz, x/sys; purego leaves with `spikes/`); about 300 lines per backend plus 100
  shared, estimated from the spikes; no C or Objective-C in the tree; Linux stays `CGO_ENABLED=0`, darwin needs cgo at build time.
  `pins/` gains six `trusted` rows (firecracker, kernel, image; amd64 and arm64): first start fetches 7.5 MB, a kernel of 17 to
  48 MB and an image under 400 MB, inside P2's 60 s on an ordinary link.
- Firecracker's host floor is a validated kernel of 5.10 or later; `doctor` names KVM when it is missing or not writable. Its
  teardown is 0.5 s at session end; `Kill` after the init's sync acknowledgement should remove it, and U-200 measures that.
- `--mount` (U-502) cannot use virtio-fs on Linux: it needs a file service over the channel in Go, or the Cloud Hypervisor
  fallback with a virtiofsd of our own. Decide there; clone mode (U-500) needs only the block device.

## Reversal cost

Low. Each backend is one package behind the same six methods, with one pin row or one module. Firecracker to Cloud Hypervisor is
about 300 lines and one row (both booted both kernels; exit code and shutdown already go over the channel). vz to vfkit drops a
module and adds a 66 MB row. Either host to libkrun adds purego and the A6 exceptions above. Image, init, proxy, broker and audit
never see the backend (A7); the cost rises only if code comes to rely on virtio-fs, which this decision forbids.
